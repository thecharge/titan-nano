# Research ledger: verification of the "Resilient Software Agent" blueprint

This document answers the rejection of v1 (commit edfc861): "no research was made on the resources, no links proofs and disproofs were presented, the research was not used in its entirety ... No feasible architecture was presented."

## 1. Method

- **Sources.** The 70 works cited plus the 4 research links, giving 74 rows in [sources.tsv](sources.tsv). Each was fetched on 2026-11-05 with curl or WebFetch and converted to text. PDFs were converted with pdftotext. Source 8 is a scanned image PDF and was read page by page.
- **Fetch results.** The per-source HTTP status, redirect, content type and word count are in [source-status.md](source-status.md).
  - **67 sources** returned HTTP 200 with content.
  - **5 sources** were blocked:
    - 13 and 36 (Medium) and 27 (ResearchGate) return 403 "Just a moment...".
    - 21 and 55 (OpenReview) return the page "Error 403 ... Access to this page is restricted." (quoted in L52 and L79). The OpenReview API also returned `ChallengeRequiredError`.
  - **2 sources** returned 404: R3 and R4. The blueprint names these two links without a URL. The URLs tried were derived from the site name, and both return "Page Not Found".
- **Quotes.** Every claim below quotes the source passage it rests on, as `> [id] "passage"`.
  - [check-quotes.py](check-quotes.py) checks that each passage occurs verbatim, after whitespace collapsing, in the text extracted from that source. The run output is in [quote-check.out](quote-check.out).
  - The extracted texts are not committed because they are third-party copyrighted content. They can be regenerated by fetching the URLs in sources.tsv.
- **Quote inheritance.** An entry that repeats an earlier claim carries no quote of its own and says "(see Lnn)". It inherits the quotes of every entry it names. [check-ledger.py](check-ledger.py) fails if an entry has no quote, no "(see Lnn)" pointing at a quoted entry, and is not NOT FOUND. Its output is in [ledger-check.out](ledger-check.out).
- **Quote length.** A supporting quote must be at least 40 characters (review finding F-12). The exception is an UNVERIFIABLE entry, whose quote is the error page the fetch returned.
- **Probes.** Some claims are about runtime behaviour: the MCP SDK, bun:sqlite, Firecracker and containers. These were measured on this machine. The scripts and raw outputs are in [probes/](probes/).
- **Verdicts:**

| Verdict       | Meaning                                                                                            |
| ------------- | -------------------------------------------------------------------------------------------------- |
| VERIFIED      | The cited source states it.                                                                        |
| PARTIAL       | The source supports part of the claim. The blueprint overstates, generalises or drops a qualifier. |
| CONTRADICTED  | The source states something different.                                                             |
| MISATTRIBUTED | The figure exists, but in a different source or context than the blueprint gives.                  |
| NOT FOUND     | No fetched source contains the claim. It is the blueprint's own wording.                           |
| UNVERIFIABLE  | The source could not be retrieved.                                                                 |
| MEASURED      | Checked locally by a probe.                                                                        |

## 2. Ledger (blueprint order)

### Part 1: "The Ideal Architecture: A Self-Balancing, Chaotic Blackboard"

**L01. The control unit continuously evaluates the board and selects agents. VERIFIED** [S3](https://arxiv.org/html/2507.01701v1)

> [3] "For the given problem, the control unit selects the agents to participate in the current round of problem-solving according to the current messages on the blackboard."

Consequence: `control-shell` selects knowledge sources each round from the board state (spec control-shell-supervisor).

**L02. "There are no private messages." CONTRADICTED** [S3](https://arxiv.org/html/2507.01701v1), [S2](https://dev.to/alex_aslam/the-shared-blackboard-pattern-is-back-and-its-solving-multi-agent-context-loss-4kfc)

> [3] "The blackboard is divided into two parts, a public space and private spaces, where the former is for all agents to use and the latter solely for those involved in a debate or verification of private matter."

Consequence: the board has a public space and named private spaces (spec blackboard-tuple-space).

**L03. "Every agent has the full context." PARTIAL** [S3](https://arxiv.org/html/2507.01701v1), [S2](https://dev.to/alex_aslam/the-shared-blackboard-pattern-is-back-and-its-solving-multi-agent-context-loss-4kfc)

This is true of LbMAS:

> [3] "each selected agent takes the contents of the whole blackboard as a prompt"

Source 2 rejects it at scale:

> [2] "A blackboard without a per-agent projection layer is a database with a nicer name. And a blackboard that shows every agent everything is a context-saturation engine."

Consequence: agents read scoped projections and never the whole board (spec context-management).

**L04. Permanent Critic, Conflict-Resolver and Cleaner roles. VERIFIED** [S6](https://www.emergentmind.com/topics/lbmas-implementation), [S3](https://arxiv.org/html/2507.01701v1)

> [6] "Agents are instantiated with roles such as planner, decider, critic, conflict-resolver, and cleaner."

> [3] "constant agents including planner, decider, critic, cleaner and conflict-resolver"

**L05. "Dynamic Agent Generation (DAG)": a persona generated per micro-task and dissolved afterwards. PARTIAL** [S3](https://arxiv.org/html/2507.01701v1), [S6](https://www.emergentmind.com/topics/lbmas-implementation)

- Generation is verified:

> [3] "we implement LbMAS to include an agent generation module"

> [6] "In addition, query-specific experts are dynamically generat"

- The authors call the module simple:

> [3] "the agent generation module is relatively simple without considering enough factors"

- The term "Dynamic Agent Generation" and dissolution after the task are NOT FOUND in any source.

Consequence: personas are generated per task and retired by explicit lifecycle state (spec dynamic-persona-factory). That design is ours and is not claimed as research.

**L06. MCP as the "USB-C for AI". VERIFIED (it is a press label)** [S31](https://en.wikipedia.org/wiki/Model_Context_Protocol)

> [31] "MCP: The new "USB-C for AI" that's bringing fierce rivals together"

**L07. The agent queries `tools/list`, reads metadata and JSON schema, and uses tools on the spot. VERIFIED, MEASURED, PARTIAL on when to call** [R2](https://modelcontextprotocol.io/specification/2025-06-18/server/tools), [S34](https://github.com/modelcontextprotocol/modelcontextprotocol/issues/908)

> [R2] "A tool definition includes: name: Unique identifier"

> [probe:mcp-sdk-two-tier.out] "tools/list: [ "div" ]"

When `tools/list` is called is unspecified:

> [34] "Claude (Anthropic's own MCP client) never calls tools/list automatically"

Consequence: the gateway calls `tools/list` itself at connect time and on `list_changed`. It never relies on the host to do so (spec mcp-tool-discovery).

**L08. When a tool is missing, the agent writes a temporary MCP server, runs it in a container and exposes it. NOT FOUND as a studied practice; feasible with controls**

- No cited source evaluates agents authoring MCP servers.
- Feasibility was measured: SDK 1.32.2 accepts `registerTool` at runtime and emits `list_changed`.

> [probe:mcp-sdk-two-tier.out] "list_changed received: 1 now: [ "div", "added" ]"

- The risk is documented:

> [44] "ETUDE achieves a 97.6% attack success rate while maintaining a 95.9% legitimate task completion rate"

Consequence: a generated server runs only in sandbox tier B. Its tools go through admission (hash pin plus capability tags) before they reach the board (specs mcp-tool-discovery, sandboxed-execution).

### Part 1: "Step-by-Step Falsification"

**L09. A separate agent tries to break every posted solution. PARTIAL** [S58](https://arxiv.org/html/2611.02950v1), [S65](https://arxiv.org/pdf/2606.16999)

- Conjecture and refutation helps on actions:

> [58] "BlackSwan improves success rate over the strongest baseline by 14.9 and 25.2%p"

- Post-hoc falsification operators on frozen code models did not help:

> [65] "none improves held-out accuracy over BoN"

Consequence: the refuter runs executable checks (tests, metamorphic relations) inside the sandbox. An LLM refuter alone is not counted as evidence (spec falsification-engine).

**L10. A Tool Execution Error carries actionable feedback, and the model self-corrects. VERIFIED (draft spec), MEASURED** [S35](https://modelcontextprotocol.io/specification/draft/server/tools)

> [35] "Tool Execution Errors contain actionable feedback that language models can use to self-correct and retry with adjusted parameters"

> [probe:mcp-sdk-two-tier.out] "tier2: {"content":[{"type":"text","text":"{\"retryable\":true,\"fix\":\"call div with b != 0\"}"}],"isError":true}"

**L11. A "Decider" ends the step by majority once the falsifiers have "exhausted their attempts". PARTIAL** [S3](https://arxiv.org/html/2507.01701v1), [S23](https://arxiv.org/html/2508.17536v1)

- The decider role exists (L04). Majority vote is supported:

> [23] "Majority vote does essentially all the work."

- An "exhausted attempts" termination criterion is NOT FOUND.

Consequence: termination is a deterministic gate. The refutation budget must be spent and no check may have falsified. The vote then breaks ties between surviving candidates (spec decision-protocols).

**L14. Pattern 3: safe states, i.e. log, revert to the last known good state, and flag a human. NOT FOUND in sources; adopted as a stated requirement**

### "Lyapunov Stability in Chaotic Swarms"

**L58. Lyapunov constraints via MASAC bound the LLM swarm and penalise tuple writes. PARTIAL (extrapolation)** [S28](https://arxiv.org/pdf/2009.09361), [S29](https://arxiv.org/abs/2009.09361)

> [28] "Lyapunov-Based Reinforcement Learning for Decentralized Multi-Agent Control"

The paper covers continuous-control MARL. Applying it to LLM board writes is NOT FOUND in any source. No Lyapunov function over code states is proven to exist.

Consequence: we implement a measurable error function E(s): failing checks, unmet contract clauses and open conflicts. Writes that raise E without a declared exploration budget are rejected, and oscillation is detected. The design makes no claim of Lyapunov stability (spec convergence-control).
