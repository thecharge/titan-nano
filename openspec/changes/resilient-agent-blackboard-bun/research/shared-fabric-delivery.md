This sequence refines owning tasks 26.3–26.5, 28.2–28.4, 33.12 and 33.19 and repair tasks 2.3–2.4. It does not replace their acceptance scenarios or mark them complete. ## Observed starting point

The runner coordinates static file scopes across runs in one engine, records waiting/acquired/released intent, allows overlapping readers and preserves queued writer precedence. The earlier hierarchical draft admitted a parent reader with a descendant writer and was rejected after a separate probe. Regression cases now cover both conflict directions and arrival orders. Source-focused tests exercise both pinned SDKs concurrently in one working directory and cancellation of one peer. A separate process fixture exercises graceful and killed lease owners. Unscoped native turns retain exclusive admission. These are useful components, not complete shared-fabric acceptance.

Exact execution bindings now have source and installed evidence plus stricter focused script follow-up cases. The delayed-check guard now conservatively compares the complete retained readable project view, including files outside declared writes, because arbitrary native and script reads are not observed. Restart cases preserve an unchanged dependency and refuse a changed or deleted dependency before a new check. This fallback can invalidate an independent writer and does not establish managed read observations. Missing behavior includes dynamic read observations, expanding claims without holding the earlier scope, automatic reconciliation after external edits, and protected writes for native tools and scripts. Host catalogue records now carry the board execution binding. That binding does not establish read observation or protected writes. Full-tree capture still happens before declared-path filtering; a concurrently changing unrelated file can therefore invalidate capture. This is a further limit on claiming independent writing runs are delivered. Existing received-result receipts prevent blindly dispatching a received result again but do not complete reconciliation after capture failure.

## Completion rules

Keep the owning tasks and repair tasks open until their complete mapped cases pass. A passing lease primitive does not establish negotiated execution. A passing vendor stub does not establish live vendor behavior. Do not advance a task merely because its source exists or a neighboring scenario passes. Preserve failed evidence and the exact tested source identity in the repair records. Broader product backlog and separately authorized paid calls remain tracked in their existing owning tasks.
