## Setup

Use the Bun version pinned in `package.json`. Install dependencies with `bun install --frozen-lockfile`, then run `bun run hooks:install`. Prepare the offline test image and pinned model dependency separately with `bun run test:prepare`, following the pinned image instructions in the [preview guide](preview.md).

The prepared test model lives under node_modules/.bun/titan-model. Staged exports share that dependency-cache tree, and offline verification mounts it read-only. Keep the model there so staged verification can inspect the same digest-checked artifacts without downloading them or writing into the exported source tree.

Routine commit and push checks do not install dependencies, pull images, build the product or call vendors. Missing tools or a changed lockfile stop verification and give setup instructions.

List each manually changed file with a `Written by hand` trailer in the commit message. For a long path, put `Written by hand:` on its own line and indent the complete path on the next line. Each file still needs its exact path. An unindented following line and an empty continuation provide no attribution.

## What the hooks check

The commit hook exports the index into a temporary directory with a separate Git index. Checks read that exported content. An unstaged fix cannot hide a staged defect; an unstaged recreation cannot undo a staged deletion. The snapshot checks preserve the working files and index. Before that export, the commit hook formats staged source and documents, then stages its formatting changes. Temporary exports are removed when a check succeeds or throws.

Workspace dependencies in the export resolve to exported workspace code. External dependencies come from the prepared cache and must match the declared pinned versions. The snapshot lockfile must match the prepared checkout. Symbolic links and submodules in tracked content are currently rejected because snapshot containment for them is not implemented.

The message hook scans for secrets before checking Conventional Commits. The push hook reads Git's advertised updates and inventories every outgoing commit, including an earlier commit followed by a fix. It exports and checks each revision. A branch with no remote base includes its history; a missing advertised remote object requires fetching before retrying. A successful complete gate records its exact Git tree locally. The push hook can reuse that result for the identical tree after validating the hook policy and commit metadata. Changed content requires a new complete gate.

The snapshot gate reports its selected scope. A nonempty change containing only regular Markdown under `docs/` or `openspec/`, the root README or a declared workspace README uses documentation scope. The exact active change acceptance map also uses that scope when both file modes are regular or absent. Its specification check still validates every mapping; malformed or missing evidence fails. Unknown tabular files, executable or symbolic map files, source changes beside the map and unresolved comparison bases retain full scope. It retains every non-test stage, secret scanning and commit-message validation, and omits only the offline product suite. It does not build or reuse a previous result. Run the usual commit and push commands; no bypass flag is needed.

Selection compares explicit Git trees. Commit uses HEAD and the staged tree. Push still checks each outgoing revision against its first parent, so an earlier source change cannot hide behind a later guide edit. Rename detection is disabled to retain both removed and added paths. Source changes, unknown ownership, executable modes, malformed or oversized metadata, missing bases and new references keep the full suite. An empty comparison also keeps full scope for a clean local revision. Package dependency selection and reusable receipts remain separate work.

Secret checks use the exported tracked-file inventory, including force-added ignored files. They do not use the working tree's ignore rules to decide whether a tracked file is safe. Push verification also checks commit messages.

The current snapshot gate checks hook policy, secrets, Biome, TypeScript, pinned local documentation formatting, package boundaries, capped promise use, spelling, specifications, documentation and the offline test suite. A failed stage keeps the result unsuccessful. Unused-code verification now also runs through the admitted workspace policy described below. The remaining reference rules still need their own jobs and adversarial fixtures. Their absence is a delivery gap, not an accepted exception.

## Capped parallel work

Use `all` from `@titan/core` with lazy tasks: `await all(items.map(item => () => work(item)), limit)`. The default cap is eight. A task failure stops queued admission, drains active tasks and rejects with the first failure. Use `settle` when every queued task must run and each outcome must be retained. Both helpers preserve input order. Starting promises before passing them to a helper cannot cap their execution. The engine already caps admitted agents and uses settlement only to drain its admitted work.

`bun run check:promises` rejects direct and computed `Promise.all` and `Promise.allSettled` members in owned source. The same check blocks staged commits and every outgoing revision. Dependency files and generated build output are outside owned source. The checker reads source through a byte-limited stream before parsing it. A source over the limit fails verification.

`bun run check:async-fs` checks the same owned source inventory. Use explicit promise filesystem imports or named stream APIs. Synchronous filesystem imports and reexports fail, including aliases. Default and namespace filesystem imports, direct CommonJS or dynamic access and direct builtin-module access fail because they hide callable members. Fixture source strings remain data. The shared source reader bounds bytes before parsing. This check runs in staged and outgoing snapshot gates; its failing-stage fixture also prevents silently dropping the job. It is a source rule, not a replacement for the offline operating-system boundary.

## Bounded byte reads

Use `readBytes` or `readFileBytes` from `@titan/streams` before parsing bounded documents. Limits belong to `IoLimit` in constants: configuration documents use 1 MiB, server discovery uses 8 KiB, checkpoint hashes use 128 bytes and HTTP response documents use 16 MiB. The collector copies reused chunks into fixed pages and closes active iterators on failure. Files open only after budget validation. Structured parsing still retains the final bounded document; transport owners must supply timeouts or cancellation for pending reads.

Use `jsonBytes(value, maximum)` from the same package when constructing bounded JSON data. It escapes fixed-size string segments, counts expanded UTF-8 bytes and rejects unsupported values, accessors, sparse arrays, custom prototypes, cycles and excessive depth. It supports plain JSON data without custom serialization hooks. The caller must still choose the budget and admit any enclosing transport frame. The runner uses it before persisting each task and opening a session, with a 1 MiB budget for the complete prompt including checker inputs and candidate. The host uses `jsonByteLength` to count complete frame bytes without accumulating the serialized document. This synchronous CPU check preserves protocol callback ordering and performs no I/O. Its bounded counter traverses containers directly, avoiding recursive generator delegation while preserving the encoder’s strict data rules. Object key escaping and delimiters count against the complete UTF-8 allowance. Managed backends validate complete turn data before execution accounting, and direct transport calls validate before process creation. The journal also counts strict JSON before serializing a record within 16 MiB and writes a compact state projection within the same allowance. Failed admission leaves sequence and durable state untouched. Other serialization paths require separate migration; this does not establish bounded serialization everywhere.

For larger JSON projections, use `jsonStream(value, maximum)` with `atomicWriteStream(path, source, maximum)` from board. The encoder yields independent pages of at most 64 KiB; the writer also enforces its own complete byte limit. Late encoding or producer failure removes temporary bytes and preserves the previous file. Publication still requires file sync, rename and parent-directory sync. A failure after rename may already have published bytes and requires journal reconciliation. This avoids accumulating the complete encoded projection; it does not remove the original structured data from memory.

## Owned command capture

Use `captureCommand` from `@titan/process` for authorized local control commands. It returns separate binary stdout and stderr Buffers and the normal exit code. Validate settings through the shared `CommandCaptureOptionsSchema`. Each pipe defaults to one MiB and the deadline defaults to ten seconds. Callers can lower the byte ceiling and select a deadline up to ten seconds. Packaging retains its one-MiB and ten-second maximums and rejects completed nonzero exits.

Pass cancellation explicitly. The owner closes captured streams, stops the Linux process group and awaits its direct child before returning a failure. Descendants that leave that group require the enclosing container owner's cleanup. The typed `CommandProcessPort` supports isolated failure fixtures without changing global process APIs. Its default implementation is `ownedCommandProcesses`. Keep script approval, container restrictions, unknown effect reconciliation and workflow usage in their respective owners.

Missing, malformed or live legacy owners are refused, including possible process-id reuse. Home storage must provide reliable local SQLite locking.
