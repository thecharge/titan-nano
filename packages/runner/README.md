# @titan/runner

`UsageHistory` incrementally accounts for consecutive committed events. Call `matches` before continuing after a policy change. Rebuild from the journal when it returns false. Repeated `finish` calls preserve eventual reporting completeness. Missing or repeated events refuse advancement.

## Responsibilities

Owns scheduling, logical quality attempts, operational recovery, worker and falsifier phases, dependency snapshot assembly and artifact delivery.

`FileAccess` coordinates scoped live readers and writers through durable claim events. Bounded admission preserves intent order while project paths resolve. Claims yield automatically on overlap; independent scopes and overlapping readers continue. A cancelled unresolved claim cannot start work. The engine owns one coordinator across its runs. Separate daemons and external programs do not share that in-memory coordinator.

## Public contract

`Engine` creates, loads, starts and controls runs through an injected backend factory. Direct engine runs start in format five. Daemon submissions provide pinned persona references and start in format eleven. Both pin runtime_version to the shared installed Titan release. The board rejects another release before replay repair or append. Formats one through four remain readable without inventing a release pin. Its internal agent-phase owner separates native turn lifecycle, event fencing, checkpoints and recovery from dependency scheduling. Task JSON is encoded incrementally with a 1 MiB expanded UTF-8 budget, including inputs, evidence and any checker candidate. Invalid or excessive task data blocks before native admission and remains blocked after reload without repeating completed work. Enclosing host frames retain a separate budget. The backend can validate its complete turn before counters advance or a native session opens. Oversized host metadata therefore blocks with the same unspent phase after journal reload. Task records must persist before an execution counter advances or a session opens. A failed task record blocks the same logical attempt and can resume after repair, including after reload with zero recovery retries. Successful native handles close in a finally block. `Capacity` limits active agents and pending callbacks across runs, serving queued runs in round-robin order. Cancelling queued work releases its waiting slot. Queue saturation blocks the same logical attempt before starting an execution or session. Explicit resume can admit that work after capacity becomes available, including after reload. Passed phases and native session identifiers are retained durably through board commits. Independent ready nodes can run in parallel.

Run the complete offline engine suite. It covers mixed plans, retries, restart recovery, refutation, malformed verdicts, file conflicts and cancellation while waiting for capacity. Pinned SDK process tests interrupt the checker after worker file delivery, then resume through the same or a newly loaded engine.
