# @titan/knowledge

## Responsibilities

Owns readable final knowledge files, immutable retained versions, the readable index and SQLite word search. The server opens one KnowledgeHub before announcing readiness. CLI and MCP clients delegate to that owner.

## Public contract

KnowledgeHub.open(home, settings) validates home limits, acquires a separate process-owned SQLite writer lease, replays an unfinished change and rebuilds both indexes before returning. close refuses new operations, drains admitted work even at full capacity and releases resources through one shared shutdown promise. Never delete knowledge-writer.db to clear its lock. The root exports also expose parseKnowledgeFile, parseKnowledgeEntry, knowledgeBytes and loadKnowledge. Imports admit bounded Markdown with a YAML header, or YAML personas. Existing files require a UUID and positive version. Invalid UTF-8, unknown fields and exceeded byte allowances fail. Newlines normalize to LF; retained history preserves the original bytes.

Add, get, update, delete, search and reindex run through one bounded queue. Updates and deletes require the observed version. An update cannot change kind. Before publication, the owner checks active entry, file and readable-index budgets, then syncs a change journal. It preserves the previous file, replaces the final file through an atomic rename, repairs SQLite and INDEX.md, and removes the journal before acknowledging. A publication failure fences the owner until reopen. Replay is idempotent across journal, history, file and index boundaries. The entry files remain authoritative. Reindexing can repair a missing database after owner restart.

Persona registration uses the same writer queue and journaled publication as other hub changes. Use hub.registerPersonas(workflow) when the hub is already open. The standalone registerPersonas(home, workflow) opens and closes its own owner. Concurrent registrations through one owner allocate distinct versions for changed personas and reuse unchanged versions. Published versions are immediately visible in the catalog. Interrupted publication recovers on reopen. Each mutation allocates a distinct version even when its changed fields match another mutation.

The daemon registers personas and retains the run's persona references before execution for every submission transport. Saved persona references and mutations resolve before backend preflight. The run pins the resolved execution plan alongside its original source plan, source bytes and workflow revision. Retry and restart reuse the retained binding. CLI checks resolve references without registration.

New allocations made during submission binding retain an immutable hashed registration identity. Retrying the same reserved submission after capture failure reuses that allocation across owner restart and intervening registrations. Standalone mutation registration still allocates a distinct version. Mutations inherit omitted tools and tags from their parent. An explicit empty array clears the corresponding field.

Open calls query the daemon's bounded persona catalog through the same owner queue. Selection considers eligible lifecycle states and every requested tag. Each pick retains its version, random seed and eligible versions on the board. Proposed and retired personas remain excluded. Human-approved lifecycle changes remain pending production integration.

Quality publication evaluates Wilson transitions from unfaded worker counts and retains each move with its causal result and bounds. A weak version retains an improvement request with the same publication. Terminal recovery forwards that request to the run ledger. Replay recovers interrupted delivery and deduplicates an acknowledged request. Its arguments include the persona, refutation count and board run/version reference for the full evidence. Automatic retirement, deletion and merge handling remain pending.

Word search uses parameterized FTS5 queries and highlights matching words. Kind-only search lists matching final entries. Results include a snapshot revision, paths and versions. Count is capped at 200 and retained result metadata at 1 MiB; truncated reports a byte cutoff. With a configured local embedding runtime, both mode combines word and meaning results. Missing model files leave word results available with a warning. Explicit meaning mode reports unavailable setup. Normal search uses verified local model files offline. Generic deletion refuses personas until a human-approved deletion path exists.

commit accepts a stable publication_id and distinct mutations containing id, observed version and draft entry. A null version adds; a null draft deletes. It checks all versions and aggregate budgets before recording durable intent. One publication journal covers the set, and one SQLite transaction and readable-index revision follow the file writes. API readers queue behind publication; individual files are replaced separately, so out-of-band filesystem readers do not have a multi-file atomic snapshot. Recovery completes the journal before readiness. Durable receipts under .publications let identical retries return the original result, even after later commits; reusing an id with different input conflicts. A failure after intent fences the owner until reopen. Receipts do not authorize an agent or publish a candidate by themselves.

attempts is the host-owned private-set store on the same owner. Scope includes run, step, nullable part, candidate and logical attempt. stage replaces a bounded private proposal using its observed revision; read survives restart. These proposals do not enter final get or search. publish prepares the private record only after final admission succeeds, then uses the stable publication id and retains its receipt. Reopen and retry complete interrupted publication once. Ordinary version conflicts leave the proposal open and can be discarded. discard clears an open proposal and retains a tombstone; prepared or published records cannot be discarded or reopened. Closing drains accepted work. A failed final publication also fences private operations already queued behind it.

These methods are internal host capabilities exposed through the owner, not authenticated agent tools. Scope identifiers do not grant authority. Storage isolation does not establish operating-system confidentiality from agents with unrestricted access to the same home. The runner decides publication for the currently supported single candidate. Multi-candidate selection and native tool authorization remain required.

## Verification

The knowledge-view-search suite covers private word matches, kind filters, final-version exclusion, restart, queued searches, failure fencing, closed proposals and byte limits after adding scoped metadata. The knowledge-view suite covers scoped CRUD, copied scopes, read-own behavior, revision conflicts, concurrent edits and pending-add cancellation. The knowledge-runner and knowledge-runner-recovery suites cover kept publication, refutation disposal, whole-set conflicts, final candidate hash verification and publication recovery without repeating completed phases. The knowledge-attempts, knowledge-attempt-safety and knowledge-attempt-queue suites cover private restart, revision conflicts, receipt integrity, discarded-set refusal, bounded admission and owner failure and shutdown. The knowledge-commit and knowledge-commit-safety suites cover whole-set conflicts, budgets, mixed changes, snapshot readers, damaged receipts, link refusal and safe version limits. They also interrupt journal, file, history, index and receipt boundaries. The integration suites knowledge, knowledge-surface, knowledge-http, knowledge-client and knowledge-files use flat case tables and shared factories. They exercise retained bytes, optimistic conflicts, publication interruption, restart, projected-index loss, bounded admission, malformed input, response identity and HTTP, CLI and MCP parity. The knowledge-writers end-to-end suite uses eight separate resident CLI applications, each in its own process, with 300 updates per process. Each CLI process uses the same bounded GC-marker environment and small-heap mode as managed native hosts. A start barrier gives every writer the same first version. It reconciles commit receipts, conflicts, every retained version, final search and daemon restart. Stale writers use an unchanged base version; direct executable probes also verify conflict output and exit code 2. The installed-package probe uses the actual packed command and MCP stdio service. Full check and installed results are recorded in the active change's knowledge-hub delivery record after observation.

## Limits

Home-owner server.knowledge settings bound active entries, entry bytes, index bytes, active entry bytes in total and pending queue operations. Optional max_publication_entries, max_publication_bytes and max_publication_receipts lower the set-count, journal-byte and retained-receipt ceilings of 32, 16 MiB and 10,000. Each receipt is bounded at 64 KiB. A full receipt allowance refuses new publications while identical retries remain readable. Existing settings keep their original shape when these optional fields are absent. Receipts currently require operator-managed retention after stopped-owner inspection; automatic pruning is not implemented. Optional attempts.max_sets, attempts.max_entries and attempts.max_bytes lower private-set ceilings of 10,000 records, 32 mutations and 16 MiB per staged document. Published and discarded records retain their slots. Recovery metadata has a separate hard allowance for its receipt. Automatic private-record retention is not implemented. They do not bound retained history or SQLite disk allocation. Symlinks, hard-linked files and non-regular entry files are refused. External editors must stop the owner before editing canonical files, then restart or reindex; edits during publication can require manual reconciliation. The owner also exposes commit for a bounded host-owned change set. Native workers use execution-scoped project proposal tools and local meaning search is available after model setup. Multi-candidate selection and human-approved persona lifecycle operations remain open. This package is not production acceptance for the full product.

`hub.view(scope)` provides host-owned add, get, update, delete and word search methods for one private attempt. Every write requires the `private_revision` returned by the last read or write, or null when the attempt has no private set. Entry versions describe the proposed final entry; repeated edits coalesce into one mutation against the original final version. Deleting a pending addition cancels it. Persona deletion always requires the approval path. These methods cannot publish or discard a set.

The owner can read its pending entries; other scopes and final hub reads see only committed entries. Publication and disposal close the view to writes. Scope ids are not credentials. Native tool authorization is still pending; this host API does not establish an agent security boundary.

Private search holds the private queue while it acquires the final queue, matching publication lock order. It returns the private revision and committed revision together. An in-memory FTS5 database uses the same token handling and kind filter as public search; it closes after the query has completed. Pending ids, including deletions, are excluded from the final SQL query before its limit. Matching private entries precede final matches; each group retains its existing rank and id order. Pending results point to their private proposal document and report pending visibility. Final results keep their canonical paths. The count and byte ceilings still apply after those fields are added. Published and discarded proposals do not add private results. The public index and public search are unchanged by private search.

## Run service ownership

`ownedKnowledge` supplies one bounded project queue for native tools, private attempt publication, lessons and journals. The server passes its open home hub. Project owners close after each serialized operation. A shared project and home path reuses one hub. `ownedRunHub` retains the narrower run-service interface for programmatic workflows, opening and closing a temporary home owner when needed.

Native tools resolve the project from the host-owned run. Worker writes enter that project's private attempt, while reads also include committed home knowledge. A pending project deletion hides a home entry with the same identity. Checkers read committed entries and cannot publish private proposals. The runner publishes checked proposals or discards refused attempts through the same project queue. Existing home attempts retain their original publication owner. Duplicate project and home attempts with the same scope refuse ambiguous ownership. This routing does not enforce filesystem confidentiality against unrestricted external programs.

Merged project and home search results retain project precedence and apply the shared result-count and serialized-result byte budgets after adding scope or visibility fields. Truncation remains explicit. `testing/integration/knowledge-merge-bounds.test.ts` covers committed and private pages, including escaped metadata whose merged bytes exceed the budget.

## Operator inspection

`titan kb prune` reports exact duplicates, replaced versions and entries never read for ninety days. `--before` accepts a UTC cutoff. `--apply` archives selected entries through bounded, recoverable publications. Reports leave entry files and read counts unchanged.

`titan kb consolidate` reports groups with matching kind and complete body. Applying a group creates one entry with every source id and the union of their tags. Full source text remains in history. A group must fit the existing atomic publication and entry limits.

`titan kb restore ID` restores the latest archived text at the next version. It refuses active identities, malformed history and linked paths. Generic add cannot reuse an archived identity at version one. These commands select the project hub by default and accept `--scope home`. Canonical personas retain their approval-driven lifecycle.

`inspectKnowledge(home, embedder?, settings?)` returns a bounded read-only client for committed metadata, entries and stats. It does not create missing hubs, repair files or record entry reads. Mutation methods and question search are refused. Entry reads verify the selected identity, version and indexed content hash.

`inspectPendingKnowledge(home, query?, settings?)` reads private proposal metadata without publishing it. Open and prepared records name their run, step, part, candidate and attempt, plus add, update or delete. Deletions use read-only committed metadata. Closed records are excluded. Directory, document, mutation, page-count and serialized-byte budgets remain enforced. Non-regular roots and proposal files are refused. The operator CLI supplies this reader for `titan kb list --state pending`; final listing remains the default. Different attempts proposing the same entry retain separate rows. This does not expose private entries through the ordinary agent HTTP knowledge endpoint.

## Read-only history and dates

The client history operation accepts an entry id, optional exclusive before version and limit. The default limit is 50; the maximum is 200. Returned entries descend from the selected version and retain their parsed bodies. Each page has an 8 MiB serialized-entry budget and a nullable next_before cursor. Passing that cursor requests the next older page. The current version is separate from retained versions. Missing, changed, linked or malformed history fails rather than skipping evidence.

Ordinary and inspection readers share history validation. History reads do not record entry usage or publish pending changes. Inspection retains the database bytes. Statistics expose oldest and newest file modification dates for each kind and the whole scope. Empty kinds retain null dates. Repeated inspection recalculates dates from current files.

Persona quality history is published by the daemon during terminal journal delivery. A result retains its run, step, part, candidate hash, attempt, reconciliation generation, role and verdict. Identical replay preserves the entry version. A conflicting verdict for an existing identity is refused. Worker survived and refuted totals, distinct run counts and checker refutation counts are visible through persona search. Persona definitions retain their registered version while the containing knowledge entry versions each history update. Interrupted execution usage remains in the run board. Earlier runs without pinned references receive no inferred quality outcomes.

Each persona version retains up to 4,096 result records, within the owner's existing entry and total byte limits. Exceeding a limit refuses publication and leaves terminal journal delivery pending for inspection and recovery. Automatic history compaction and lifecycle approval transitions remain pending.

Terminal journal delivery also publishes backend usage for each pinned persona version. Its usage field retains per-run reports, physical execution counts, known token and cost subtotals, and completeness for each measure. Worker, checker and reconciliation usage follows the runner's existing backend accounting policy. Interrupted starts retain unreported execution counts. Identical reports leave the canonical version unchanged. A newer committed prefix replaces the earlier report for that run. Conflicting totals, decreasing known subtotals, foreign identities and future cursors are refused. Separate runs contribute separate reports. Publication uses the existing writer queue and recovery journal.

New persona versions start with complete usage history. Older canonical records without usage remain readable, and inspection returns history_complete false with incomplete measures. Later reports preserve that historical uncertainty. Usage reports share the 4,096-record ceiling and canonical entry byte limits. Automatic report compaction remains pending. Usage publication and completed quality outcomes have independent counters.

Registered persona definitions retain their name, version, parent and definition across ordinary updates and batch publications. Definition changes require a newly registered version. Existing lifecycle and history metadata publication remains available.

`titan persona show NAME --home HOME --json` reads saved definitions, states, counters and retained quality history, newest first. Completed worker and checker uses persist with each deduplicated outcome. Older records derive uses from retained unfaded worker totals and retained checker history. Older checker results absent from both retained history and stored counters cannot be reconstructed. Use `NAME@VERSION` to inspect an exact version. Use --limit to bound the page and --before with the returned next_version to continue. The page reports has_more. Inspection includes retired and deleted records retained in the catalogue, verifies the canonical file and leaves the hub unchanged. It runs without starting a daemon. Missing names, missing versions and malformed selectors fail explicitly. Approval-driven lifecycle commands remain pending.

Word, meaning and private-attempt searches hide retired and deleted persona entries before applying their result limit. The CLI accepts `titan kb search --kind persona --all` for explicit inspection. HTTP and MCP use the optional boolean `all` search field. Direct entry reads retain historical access. The derived hidden-persona index is created on existing databases and rebuilt from canonical files during startup and reindex. Meaning search removes hidden entries from its active projection and restores them for an explicit all search.

A completed checker pass followed by a refuting persona or script check for the same candidate records later_refuted in its outcome. The persona counter falsifier_passes_later_refuted increments once through the existing replay-safe publication. Earlier refutations and later passing checks leave that counter unchanged. Inspection exposes the counter alongside falsifier_refutations. Older outcomes without this observation retain their recorded information. The service cannot infer missing historical script verdicts.

Completed worker verdicts retain separate sampling counts. Each new verdict multiplies the counts of every canonical version with the same sorted tag set by 0.98 before adding its reward. Matching peer updates and the target quality history share one recoverable publication. Replayed results return before fading. Interrupted executions cannot train the counts. Wilson and retirement totals retain their unfaded integers. Production open calls use the separate sampling counts when present. Legacy records initially use their retained raw totals or completed worker history. Historical fading cannot be recovered from earlier aggregate totals. Existing publication entry and byte limits refuse an oversized group before writing its intent.
