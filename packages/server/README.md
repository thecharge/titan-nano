# @titan/server

`RunSummaryProjector` publishes dashboard numbers from the committed event stream. Its least-recently-used history cache shares the configured resident-run bound. Consecutive compatible events advance existing reducers. Missing history, changed plans, changed usage policies or a cursor gap rebuild from the journal. Projection failure drops the cached history. Stateless reconstruction streams usage and numbers in one pass.

Server composition supplies exact owned runtime paths to new runs. When home is inside the project, snapshots omit the server databases and companions, credentials, discovery, ownership metadata and managed knowledge storage. Neighboring project files and other SQLite databases remain subject to strict snapshot validation. These omissions are persisted with the run; an arbitrary client cannot submit an omission list.

Server ownership is held by an exclusive SQLite transaction for its lifetime. New owner records mark that lease-backed protocol. After successfully acquiring the kernel-held lease, a replacement can reclaim such a record even if its old PID now identifies another process or belongs to another PID namespace. Legacy records retain their live-process check. Occupied leases and malformed records still refuse startup before replacing ownership metadata.

## Responsibilities

Owns the authenticated loopback HTTP service, typed HTTP client and MCP bridge. Run operations share the same engine and per-run serialization.

The knowledge owner opens and recovers before readiness. Authenticated POST /knowledge accepts a strict operation and input envelope for add, get, update, delete, search and reindex. It shares the same credential and Origin checks as run operations. Unknown fields and query parameters fail. Stale entry versions return 409, missing entries 404 and persona deletion 403. The ./knowledge export provides createKnowledgeClient, which validates returned identity, version, draft, query, mode, count and selected file paths. Main-agent MCP exposes titan_kb_add, titan_kb_get, titan_kb_update, titan_kb_delete, titan_kb_search and titan_kb_reindex. These final-entry operations do not grant native agents private attempt tools or bypass persona approval. See the knowledge package README for storage and recovery limits.

Production runs read project and home knowledge before dispatch and save lessons and terminal journals in the project hub. A bounded queue serializes project hub ownership, and a project using the server home reuses that owner. Source and installed CLI acceptance cover restart, later journal consumption, refused attempts, project separation and an unavailable project hub. Native execution uses the authenticated broker for tools. Public terminal and blocked snapshots wait for journal finalization, and shutdown drains this work before closing the hubs. Complete project-scoped native tool routing remains pending.

Live runs share the project tree. The engine records scoped read or write claims in each run's board. Readers may overlap; an overlapping writer yields until earlier claims release, while independent scopes continue. Waiting spends no vendor execution or quality attempt, and cancellation withdraws the claim. Undeclared write scope conservatively covers the project. These cooperative claims belong to one engine and do not fence external programs or another daemon.

Journal delivery failure keeps its intended outcome in the board and exposes the run as blocked. Resume retries delivery without dispatching cancelled or finished work. A newer cancellation replaces the earlier pending outcome. Stable journal identity prevents duplicate entries after acknowledgement loss and preserves versioned amendments. Existing journals with historical random identities are not migrated.

## Public contract

The root export also provides `scopedScripts`, the bounded production script service composed with an engine owner. It validates run, step, attempt, phase, exact command and directory before requesting scoped approval, then rechecks permission before process dispatch. Its optional process port permits controlled component acceptance; production uses the shared process-group owner. Script and file-reconciliation answers automatically continue their waiting runs. These cases do not establish unrestricted shell confinement or publication safety after external edits.

The root export exposes server startup and client calls. `./client` exposes address loading and `createRunClient`; `./mcp` exposes the stdio MCP service. `./requests` exposes the typed scoped-request client. Responses are parsed at the client boundary. Status, resume, pause, cancel and artifact inspection must return the requested run id. A schema-valid response naming another run raises invalid_response with transport exit code four. MCP status and lifecycle handlers use these same typed methods and return tool errors for crossed responses. Submission parsing permits the newly assigned run id. External run responses and listing rows use committed snapshots, waiting for pending writes. A failed writer cannot acknowledge an uncommitted state. Listing owns per-row failure handling: unreadable runs retain their identity and diagnostic while healthy rows remain accessible. Client and MCP listing responses share summary validation. Initial starts and resumes use one background rejection handler. Server address and token records are local private files. A dedicated SQLite lease owns the home until shutdown or process death. Its persistent `server-writer.db` file must never be deleted to clear a lock. Catalog queries use Bun SQL promises and validate returned rows.

## Verification

Run submissions can request `preserve_source: true` with an absolute `workflow_path` on the shared machine. HTTP and MCP use the same admission contract. The server reads at most 1 MiB before reserving the submission and requires the file to compile to the submitted plan. Exact source bytes become part of the submission fingerprint and the run's workflow.yaml. A retry with changed source bytes conflicts even when the normalized plan is unchanged. Missing, relative, unreadable, oversized and mismatched source files leave no reserved submission. Inline submissions retain their validated YAML representation. Local authenticated clients may select a workflow outside the project directory.

Run offline server, client, MCP controls and MCP process tests. They exercise authenticated idempotent submission, malformed responses, workflow control and protocol framing. Lifecycle cases fail configuration, database opening and address publication, then require successful workflow execution after retry. The Linux Podman suite observes closed home-file descriptors and refused connections to the actual listener. Concurrent shutdown shares one completion; repeating it after another server starts must preserve that server.

## Limits

Startup resources now unwind on failure through an asynchronous disposal stack. Process tests cover SIGKILL, graceful restart, live contention and simultaneous startup. A completed run must survive restart unchanged. Legacy metadata is reclaimed only when its recorded process is absent; missing, malformed or live-owner records fail closed. This may conservatively refuse a reused process id. Network filesystems and migration from incomplete legacy startup metadata are not accepted. Shutdown during failing durable writes and interrupted installed SDK runs remain open. JSON event inspection uses bounded cursor pages across CLI, HTTP and MCP. Live server-sent event replay, complete route contracts and installed protocol parity remain open. The service is intended for loopback use.

MCP `titan_check` accepts an optional project and backend fallback. It resolves the same settings layers used for submission before checking group depth, step count and implemented Claude tool permissions. Without a project it uses the engine home. Select the later submission's project for a meaningful configuration check. This does not establish live backend readiness or complete capability support.

Run catalog responses are versioned pages ordered by descending SQLite insertion sequence. The shared selectors are `before`, `limit` and optional `client_id`. The default count is 50, capped at 200; SQL reads only count plus one rows and capped lazy tasks describe the selected rows. Follow `next_before` while `has_more` is true. Empty final pages keep their cursor. Newer insertions do not enter an older page after restart. Descriptions retain the indexed client identity and cap summary text at 4096 characters. The client binds responses to its requested cursor, count and caller. This is submission ordering with per-row committed state, not a global state snapshot or per-caller access control.

Person credentials live only in the home’s private `person-token` file. Startup creates a random token once, retains it on restart and shutdown, and refuses existing links, shared permissions, directories or invalid bytes. Reads use a bounded asynchronous Buffer and close the file before startup continues. The agent token in `server.json` rotates on restart. Both credentials authenticate native clients; any API request carrying an Origin header receives 403. Agents sharing the user account may read the person token: this is a trusted-agent limitation, not proof of human presence or separate-user isolation. HTTP request decisions are described below; CLI decision commands use this authenticated transport.

The decision transport creates a request with `POST /runs/RUN_ID/requests`, inspects exactly one with `GET /runs/RUN_ID/requests/REQUEST_ID`, and answers through `POST /requests/REQUEST_ID/answer`. Creation uses the strict request input schema and a caller-supplied id. Answers require `run_id`, `request_id`, observed `version`, `decision`, `reason` and answering `client_id`. The server assigns authority from the credential and refuses authority fields in the body. Agent credentials cannot answer human requests (403); stale, repeated or expired decisions conflict (409); an unknown selected request returns 404. Queries are not accepted on these routes. Per-run serialization, the engine-owned ledger and journal replay preserve one decision across retry and restart. These routes record permission decisions; they do not execute an action or resume a waiting native turn. Policy overrides and action recovery remain unfinished.

The request client admits bounded strict JSON before parsing and validates response run, request, creation scope, answer version, decision, reason and actor. Person transport reads an existing safe token file and never creates one. Only explicitly selected person commands use that transport. Stale and repeated responses are input failures; malformed or substituted responses are transport failures. This is a shared-user local service, not authentication of the supplied client labels.

MCP exposes titan_requests, titan_request_open, titan_request_read, titan_request_answer and titan_request_escalate with strict shared schemas. Successful calls return state and the complete request; state is waiting for a pending request and answered after its first decision. Creation retries preserve both states. Errors retain the HTTP error code in an MCP error result. MCP always uses the agent credential and cannot fall back to the person token or accept an authority field. Reconnecting MCP preserves the same durable request. These tools do not implement native waiting-session continuation.

Request listing returns a versioned page with query, requests, unavailable, next_cursor and has_more. Use --run-id, --client-id, --harness-session-id, --project-path and --state waiting|answered as intersecting filters. Project paths must be absolute and normalized. The default count is 20, the maximum is 100, each page is limited to 1 MiB and each call reads at most 16 runs. Continue with --cursor using next_cursor and the same filters; the count may change. A filtered page may be empty while has_more is true. Follow its cursor. Unreadable runs retain their indexed identity in unavailable. Cursors survive catalog restart and exclude newer submissions from older pages. Answers may change between pages; this is not a frozen snapshot. Origin filters support navigation and do not authorize access. HTTP GET /requests and MCP titan_requests accept the same selection. Per-run journal prefix replay remains in use.

The ./request-pages export owns strict query parsing and bounded request-page production through RequestPageSource. The source supplies a catalog database and an asynchronous per-run reader. The server serializes that read with run operations and takes a committed snapshot before ledger inspection. Corrupt source records fail the entire selected run into unavailable; the page does not invent an answer. The typed request client validates page bytes, echoed query, origin selection, count, duplicate identities and cursor progress.

Escalation is POST /requests/REQUEST_ID/escalate with exact run_id, request_id, observed version, reason and client_id. The authenticated actor comes from the credential, never JSON. The typed client always uses the agent credential for escalation and binds the returned pending human record, version, audit actor and reason. Answering afterward requires the person credential and the new observed version. HTTP, CLI and actual MCP stdio cases compare the same durable record, unchanged rejected mutations, origin-filtered waiting pages and one passed_up event. Restart cases recover the pending record before a person approves or denies.

Home-owner server.max_pending_run_operations and server.max_pending_submissions separately bound run operations and submission serialization. Both default to 4096 and accept integers from 1 through 4096. Counts include active and waiting entries. A submission uses one entry from each separate queue, allowing both limits to be one. Saturation refuses admission; explicit retry after release retains the original submission identity. Lower layers cannot override these owner settings. Legacy stored shapes remain unchanged. These queues are in memory and do not establish durable scheduling fairness.

RunSubmissions owns submission validation, configuration resolution, request fingerprints, identity serialization and run creation or journal reload. The HTTP owner delegates submission bodies to that component. Changed input under an existing identity returns HTTP 409. Exact retries retain their original run and journal cursor; workflow_path remains part of the fingerprint, including the distinction between an empty path and an absent path. Shared HTTP cases cover retained and restarted owners, discarded receipts, conflicts and unchanged quality counters.

SubmissionSchema and MCP titan_run accept an optional harness_session_id with one through 128 characters. Available run summaries retain the exact opaque label. Changed labels under a retained submission identity return HTTP 409, including after restart. The label grants no authority and supplies no durable client receipt.

Usage inspection uses GET /runs/RUN_ID/usage with no query parameters and MCP titan_usage with run_id. The strict client binds the returned run id and rejects inconsistent report counts. Known subtotals carry separate completeness flags; unreported executions prevent complete totals. Reads use the existing bounded run-operation queue.

Caller-session and project navigation adds --harness-session-id and --project-path to runs, with equivalent HTTP and MCP fields. All supplied selectors intersect. Projects must be absolute and normalized. These selections use page version two; ordinary requests retain version one. The SQL and description budgets stay count plus one and count respectively. Count bounds inspected rows, so an empty filtered page can retain has_more with a descending next_before. Continue until has_more is false. A final request with no catalog rows keeps its cursor. This is a bounded scan, not indexed lookup. Missing metadata cannot match these filters; unfiltered listing retains unavailable diagnostics. Strict client validation binds version, cursor, count and every supplied selector. Older strict clients refuse the new version.

Operational diagnostics use @titan/logger with home-owner server.logging settings. Lifecycle records use info and background failures use error with a declared code, without exception text. Authenticated health responses include finite diagnostic counters. Output uses bounded asynchronous stderr writes. A failed, incomplete or timed-out sink disables further writes without changing run state. See [diagnostic settings](../../docs/diagnostics.md).

The ./native-tools export provides NativeToolAuthority as a host-owned broker foundation. It has no public operator authority. Runtime composes scoped SDK bindings through NativeExecutions. Its owner supplies positive max_bindings and max_pending_operations limits, a validated scope and a current-execution predicate. An opaque lease credential authorizes only that copied scope and role. Worker tools use private knowledge views; checker tools read committed entries. The readiness tool reports the binding and exact tool inventory without returning its credential. The internal /native-tools route rejects Origin headers and absent, unknown, revoked or obsolete credentials. Revocation drains admitted work; queued work rechecks its binding before execution. Internal failures return generic diagnostics. The bundled stdio bridge and direct HTTP client share readiness validation. Runner lifecycle, ephemeral SDK credentials and pre-task checks have local draft coverage. Native call metadata now uses a required durable audit writer; complete tool-server acceptance remains unfinished. This broker is not isolation from arbitrary same-user filesystem access.

The ./native-tool-bridge export provides startNativeToolServer, serveNativeToolServer and NativeStdioTransport. The CLI tool-server command uses central environment validation, host readiness and exact role inventory checks before stdio service. Transport EOF triggers cleanup. See the [native connection contract](../../docs/native-tools.md) for settings and remaining native integration work.

ServerOptions.nativeTools supplies the trusted bundled launch used by automatic native executions. Runtime supplies it for source and installed service startup. The optional port keeps embedded callers explicit. Home-owner server.native_tools settings bound registrations and pending operations and set the startup timeout; project, workflow and command overrides cannot change those owner limits. The native route authenticates only its execution credential before reaching ordinary actor routes. Agent and person credentials do not grant a native role.

The ./native-executions export provides NativeExecutions, which validates launch settings before registration and validates scope and absolute run directory before consuming registry capacity. Each lease returns a volatile binding, fresh scanners for scoped and inherited secrets, a bounded value guard and a draining close operation. The server pauses active execution before stopping its listener and closing authority and knowledge. No token belongs in durable specifications, arguments or published files. Run `bun run test testing/integration/native-execution-owner.test.ts testing/e2e/native-workflow.test.ts` for the scoped owner and actual daemon cases. The native lease also refuses successful completion after an audit write failure.

The `./native-tool-client` export provides `connectNativeTools` and `nativeToolReady`. Both validate owner scope, readiness policy and actual role inventory over bounded local HTTP reads. The connection owner must close the returned client. Readiness closes it before returning. Runtime injects this behavior into HTTP adapters; the stdio bridge shares the same validation. Configuration and SDK wiring do not establish board audit or complete installed acceptance.

NativeToolAuthority requires a NativeToolAuditWriter. Every admitted MCP tool response waits for that writer, including readiness, missing-entry and unknown-tool responses. The automatic server writer resolves the persona from the matching runner phase and commits strict metadata in a tool event. Data includes scope, role, persona, declared name, outcome and returned or changed entry ids. Unknown names use unknown_tool. Bodies, query arguments, credentials and private exception text are excluded. If response inspection or the writer fails, that lease refuses later calls and successful completion. Close still drains and releases its slot; global shutdown drains all bindings. This draft has focused source coverage, including both vendors and transports; full installed acceptance and raw vendor event review remain pending.

MCP titan_run delegates submission to the typed client, which validates the assigned run snapshot. The tool acknowledges durable admission while workers continue independently. The one-second integration contract holds workers until after acknowledgement, then verifies sequential and parallel completion. Invalid plans create no worker and malformed acknowledgements return a tool error.

## Frozen configuration reports

Authenticated `GET /runs/RUN_ID/config` returns the committed configuration report with schema version, exact run identity, workflow identity and revision, journal position, saved settings, hash and sources. Query parameters and extra path segments fail. The client validates the strict report shape, selected run and effective-value checksum. MCP `titan_config` accepts the exact `run_id` and returns the same report. Reads leave the run unchanged and retain saved values after file edits and restart. Live owner ceilings and revision history remain pending.

## Stored dashboard inspection

The engine's optional committed-run projection writes a server-owned summary after journal persistence. Dashboard listing validates cached identity, journal size and modification time and does not replay a board for a stale or absent summary. Startup performs explicit legacy migration. Inactive history stays outside the engine's resident run allowance. Read-only run inspection retains partial journal tails and does not create event indexes.

Cookie-authenticated GET `/ui/api/knowledge` selects home knowledge or the project of a known run. It accepts scope, kind, tag and final/pending state filters. Entry bodies remain committed-only; combining a pending selector with an entry id is refused. Scope and per-kind counts, date ranges and model readiness describe committed knowledge. Pending rows retain operation and attempt provenance without linking to an unrelated final body. Inspection neither records entry reads nor publishes proposals. The route rejects foreign origins, missing cookies, mutations, duplicate selectors and arbitrary project paths.

The authenticated knowledge endpoint accepts the server-only history operation with id, before and limit. Its client checks entry identity, kind, descending versions, page size and cursor progress. Dashboard entry inspection renders retained version bodies as text, keeps scope and entry identity in earlier-version links, and displays per-kind dates. A before query requires an entry id and a positive safe integer. These reads use the existing operator credentials.

## Managed file observations

The `./maintenance` export provides `ownMaintenance`, `ownOfflineHome` and `requestServerStop`. Startup acquires maintenance before writer ownership. An updater can hold maintenance while an existing server remains available, then acquire offline ownership after shutdown. Resource stacks release both kernel-held leases. Lease paths and existing SQLite companions must be regular, singly linked files owned by the current user. Symlinks and hard links are refused before SQLite opens them.

Owner-authenticated `POST /maintenance/stop` accepts `idle_only`, which defaults to true. Idle-only shutdown refuses active runs and other admitted requests. Explicit owner shutdown pauses active work. Agent credentials cannot stop the server. The returned `stopped` promise lets the daemon observe completion, and `stop()` retains any cleanup error. CLI discovery also requires the daemon's release version to match the selected CLI. Automatic installation and release handoff remain unfinished.

Native personas with Read can use titan_file_read and titan_file_list through their execution-bound tool service. Reads return base64 content, a content hash and file metadata version. Missing files have a retained absence observation. Lists return regular file paths recursively under the selected directory. They describe file names and preserve the existing protected-path exclusions.

The engine commits observations before the tool response is acknowledged. Dependencies outside worker write paths are checked before capture, later checks and publication. Checkers validate every managed observation. Replaced files with identical bytes still invalidate a file read. Changed, deleted and newly created dependencies retain the existing result for reconciliation. Distinct observations share the run's frozen workspace entry allowance. Read content has a one-MiB limit. Listings have a one-MiB JSON limit.

The first managed observation promotes its run to format seven. After a closed turn observes dependencies beyond its active claim, the engine saves additional read intent in format eight. It releases the earlier claim and queues the combined read and write scope. Waiting retains completed work and quality attempts. Cancellation withdraws the queued scope. Reacquisition revalidates retained observations and candidate files. Native host admission uses the same mixed-scope overlap rule. Read dependencies grant read access. Write paths remain separately bound to execution. Worker receipts and later observations preserve newer formats and the existing runtime pin. Earlier formats remain readable. Older runtimes refuse new formats before modifying the journal. Arbitrary native and shell reads retain the complete-view consistency check. Write-scope expansion, protected process writes and automatic reconciliation remain pending.

## Shutdown admission

`stop()` closes request admission synchronously, waits for admitted HTTP handlers, pauses active workflows and drains them before closing native tools and storage. Later dashboard and API requests receive HTTP 503 with `server_stopping`. Native tool callbacks remain available while active workers are being paused. Concurrent stop calls share one completion promise.

The `./admission` export provides `ServerAdmission.use(action)` and `close()`. It bounds active handlers at the shared pending-operation limit and refuses new work after closing. Handler failure releases admission and cannot prevent shutdown drainage.

Managed daemon composition supplies its exact runtime bundle hash through `ServerOptions.runtimeBuild`. Authenticated health responses include that build header. Direct library servers advertise embedded compatibility and retain version-based discovery. Older missing headers trigger managed handoff. The health JSON body retains its existing shape.

Dashboard run projections retain journal-stamped measurements in the server catalog. Commit-time projection and startup migration use the same event and usage reducers as run inspection. Overview reads validate the journal stamp and run identity without loading historical runs. Missing, stale or malformed retained measurements rebuild during startup. The compact overview expands all recorded measurements and preserves open disclosures across refresh.
