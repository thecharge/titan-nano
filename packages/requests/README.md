# @titan/requests

## Responsibilities

`@titan/requests` owns bounded, versioned operation requests and decisions. It reads request events from the existing run journal through a typed port. Creation requires a caller-supplied request id. An identical retry returns its durable record, including after an answer; changed scope or origin with that id conflicts. Each operation binds its run, request, version, caller origin, exact scope and expiry. The default approval levels live in constants. Request and operation schemas live in types.

## Public contract

The server must share one ledger instance and its run writer for all request mutations. A ledger serializes mutations per run with a bounded queue. JSON byte admission caps each input or replayed request at 512 KiB before schema parsing; unsupported values and accessors fail before evaluation. Only the first answer to the observed version commits. Replay validates immutable scope, authority and decision time. Approval use names the expected request kind as well as its scope. Denied, expired, changed-kind, changed-scope and cross-run approvals fail. The request allowance counts all requests in a run, including answered ones; exhaustion fails rather than dropping history. Reads return at most that allowance and replay only through a committed snapshot cursor.

## Verification

Run the shared offline request integration cases. They use actual journal files, owner reloads, simultaneous decisions, bounded admission and deliberate corrupt records. Restored mutation checks cover scope, version, authority, expiry and queue admission.

## Limits

The host must authenticate the actor before calling `answer`; an actor object is not a credential. Transport authentication and script execution are supplied separately from this ledger. Sharing a user account does not prove human presence. Execution intent, uncertain outcomes and reconciliation need separate records before external actions can run. Execution-bound requests use request format two and upgrade a legacy format-one run header to format two. New daemon runs retain format eleven and their release pin. Unbound legacy records retain format one. History is not rewritten; older runtimes refuse upgraded runs.

Complete opening and answered records must fit the 512 KiB replay allowance before append. An input fitting by itself does not reserve room for metadata or an answer. Refused admission changes no committed cursor and preserves an open request for a smaller valid answer. Near-limit real-journal fixtures prove successful reload and both refusal boundaries.

Approval policy lives under `approvals` in the central configuration and generated schema. Defaults cover all request kinds. The home owner can lower configurable kinds; project files, explicitly selected files, workflows and CLI overrides can only keep or raise inherited levels. `delete_persona`, `action`, `raise_limit` and `paid_compute` always require `human`. Use `--set approvals.tool=human` on check, config or run to raise that kind through the same registry. Each run captures the effective map and its configuration hash. New requests and replay use that frozen policy, so later home changes do not reinterpret history. Legacy snapshots without the optional map keep the original defaults and unchanged hashes. An `auto` level alone does not create an automatic decision or execute an operation.

The internal `escalate` operation passes one pending main-level request to the person. It requires the exact run, request, observed version, actor and reason, and uses the same mutation queue as answers. Its passed_up event stores the complete request with escalation actor, time and reason. The request stays unanswered at version 2 and requires human authority; the later answer is version 3. Scope, origin, creation time and expiry stay fixed. Audit metadata stays unchanged in the answer. Complete record admission runs before append. Lost responses can be inspected after reload; an old-version retry conflicts rather than adding another event. These additive request fields preserve existing records without rewriting history. CLI, HTTP and MCP escalation controls share this transition. Operation execution remains open; structured request turn continuation is owned by runner.

Request capacity is configured as requests.max_per_run. It defaults to 256 and accepts integers from 1 to 256. The home owner may lower it; project, selected-file, workflow and CLI layers may keep or lower the inherited allowance. Use --set requests.max_per_run=12 on check, config or run. Every new run freezes the value and its hash. Later file edits do not enlarge that run. All records count, including answered requests. Creation retries still return an existing record at capacity; refusal of a new request preserves the journal cursor. Legacy snapshots without requests retain their shape, hash and original 256 allowance. The ledger also keeps its fixed safety ceiling. The home-owner server.max_pending_request_operations setting separately controls outstanding request mutations.

Home-owner server.max_pending_request_operations controls outstanding request mutations across runs. It defaults to 256 and accepts integers from 1 to 256, using the ledger’s central schema. The count includes active and queued mutations. Server startup validates it before admitting work and passes it to the shared engine ledger. A full queue refuses a new mutation without changing its request or journal cursor. Releasing the active operation admits an explicit retry. Project, selected-file, workflow and CLI overrides cannot change this owner setting. Restart applies a changed home allowance; individual frozen run settings do not replace that process budget. Legacy snapshots without the optional field keep their original shape and hash.

Optional origin.execution identifies the asking step, attempt, phase and execution. Admission checks it against the running phase, native session and client; the engine checks live state again at append. Opening replay checks the state recorded with that event. A completed phase cannot open a new bound request, but exact retries and later answers retain existing origins after completion and reload. These labels are audit lineage, not caller authentication. Native persona MCP registration remains unfinished. Structured request turns use openTurn with an atomic publisher supplied by the engine. The complete strict batch is bounded to 1 MiB and the frozen request allowance; each member retains the existing 512 KiB limit. Exact batch retries return retained records, while partial retries conflict. Replay requires the retained phase, original execution and exact batch membership in formats three through five.

Live bound openings also require no phase error or scheduled retry. Historical opening replay keeps the earlier lineage rules so tightening admission does not invalidate retained records. Controlled worker and checker recovery cases hold a healthy snapshot across failure and require refusal without a cursor change. Exact creation retries still return an existing record.

A waiting request execution cannot open new bound requests while its continuation is validating. This remains true if another decision commits the running step before the next native execution starts. The new execution clears waiting at its own start checkpoint. Historical replay and exact creation retries still retain their original lineage rules.

`projection(snapshot, events)` validates a supplied journal prefix without reading the port snapshot or appending events. It returns a strict versioned pending document. Runner uses this inside the board writer, avoiding a snapshot wait on that same writer. The run cursor and request identities come from the validated journal; requests.json is never read for authorization.

Request creation identity is checked by one ledger helper for both single openings and atomic request turns. An exact retained request returns before current expiry or phase admission is reconsidered; changing its kind, scope, origin or expiry conflicts. New turn members are validated independently against the captured run and clock before the complete batch receives capacity and byte checks. The existing bounded mutation queue and atomic publisher still own ordering and commit. These helpers do not add a second mutation path or authorize operations.

After type checking, run `bun run test testing/integration/requests.test.ts testing/integration/request-turn.test.ts testing/integration/request-execution.test.ts testing/integration/request-budget.test.ts testing/integration/request-record-budget.test.ts`. Member-admission cases hold an actual worker or checker execution and call the ledger with a recording publisher. They distinguish the 512 KiB complete-member limit from the 1 MiB batch limit, and check that wrong lineage and expiry never reach that publisher. These cases test admission; the existing request-turn suite separately proves journal publication and replay.

Approved persona answers may retain a strict name and definition payload. Request format three carries that answer and requires run format thirteen. Opening identity remains bound to its original scope and origin across the answer upgrade. Earlier request formats remain readable. The client validates returned definition content against its submission. Runner validates the state effect before acknowledgement and replays publication after interruption.
